# Updater crash recovery candidate — offline, not approved

The current marker contains no run identity or durable proof of teardown. `OwnedProcess` has an unnamed job and verifies emptiness only while its own handle is available. A crashed parent cannot later prove the job was empty; disappearance of a PID or job name is not evidence. Existing markers must remain held for manual investigation; this proposal does not clear them.

Candidate for future independently reviewed implementation:

1. A single local admission lock protects a durable run record with a random run ID, machine/boot identity, and a monotonic state. Persist the record before permitting any updater creation. Prevent untrusted principals from modifying records or receipts using an explicitly reviewed Windows ACL. Fail closed on malformed or unavailable state.
2. A separate supervisor owns the job and holds the admission lock through teardown. Launch the updater suspended and assigned at creation, without breakaway or inherited job handles. Prove that the actual updater and all child processes cannot delegate work outside the job (services, scheduled tasks, external processes, alternate credentials, breakaway); otherwise retain the hold. No assumption based on the stand-in test is sufficient.
3. After root exit, supervisor queries the still-open job until active process count is zero, then durably records a run-ID-bound completion receipt before releasing the lock. Only this supervisor can issue it, and it never issues it after uncertain or failed verification. Crash before durable receipt means manual hold, not automatic clearance. Durable writes and directory entry ordering require platform-specific testing, including power failure.
4. On restart, take the same lock, validate record and receipt provenance, exact run identity and complete state. A matching receipt permits channel reconciliation, not immediate publication. An absent, mismatched, stale, forged, corrupt or ambiguous receipt leaves the hold. Remove or archive the run record only as a serialized, crash-safe transition after reconciliation is safe; an idempotent state machine must handle interruption at every boundary.
5. Only after the separately held cross-host publication protocol validates the authoritative channel and immutable assets may a publisher proceed. Retain all existing publication and updater holds pending real containment proof and independent review.

The Python model expresses only the receipt decision, assuming authenticity, serialization and verified emptiness as inputs. It tests no Windows security property, filesystem durability, actual updater behavior, integration, or distributed publication. It cannot recover crashes before receipt and is deliberately not wired into production.
