# Revision 3 recovery: review-only design

**Status: DRAFT, NOT REVIEWED, NOT AUTHORIZATION TO PUBLISH.** The unconditional `AutoShip-Game.ps1` hold and the updater-teardown hold remain untouched. This document introduces no network or publication code. Independent review and explicit operational approval are required before implementation is connected to real services. No assumptions below establish the present live state.

## Goal and scope

Resume the *exact previously staged* revision 3 into the modern `game-channel`, without repacking, changing any fixed legacy manifest, deleting/replacing release assets, or relying on the locally installed game version. Existing revision 2 assets are not reused merely by name or revision. Recovery must stop if the identity of revision 3 cannot be established from preserved, trustworthy evidence. If exact recovery cannot be proven, a separately reviewed, safely staged new revision is a possible fallback; it is not an automatic substitution or permission to overwrite existing assets. A fresh revision must still satisfy the same asset-protection, serialization, reconciliation, CAS and existing hold requirements before publication.

## Evidence gates: discovery, remote verification, mutation

Read-only discovery may inspect available records without authorizing mutation. Remote-state verification requires an independently trusted manifest identity and all remote bytes, but not local staging. Upload or channel mutation additionally requires the complete authenticated inventory, validated local snapshots and the service guarantees below.

Before choosing exact recovery, inventory the original pack log, staging directory, source build completion record, channel predecessor and release asset metadata; identify which records were durably preserved and who could alter them. Independently verify hashes and document any missing chain of provenance. Check the live service's ref CAS and release-asset permissions, including all actors capable of replacement or deletion; a cooperative lock does not enforce immutability. If these guarantees cannot be established, retain the hold; neither exact recovery nor a new revision may be published. A separately reviewed new revision is a fallback only if its own provenance and the same service-safety guarantees are established.

1. An operator-approved immutable recovery inventory, obtained from the original staging record, binds repository and release identity, revision 3, exact manifest filename, manifest byte length and SHA-256, every manifest-referenced asset filename, byte length and SHA-256, game version, and provenance of these values. A manifest freshly generated from current inputs is not evidence of the staged revision. A locally observed hash alone does not prove provenance. The current audit found pack exit 0 and 22 matching sizes, but only two independently checked asset hashes and no authenticated original inventory; exact recovery remains blocked absent further evidence. Missing, conflicting, or unauthenticated evidence is a hard stop; never infer or repair it.
2. Read original manifest bytes and all local staged assets; calculate lengths and hashes directly and compare to the inventory. Parse JSON strictly, reject duplicate keys, validate the current consumer schema, revision, file/segment references, unique case-insensitive safe basenames and asset coverage, and verify all content/segment hashes required by the manifest. Reject path traversal, symlinks/reparse points, ambiguous names, and extra references. Use stable snapshots and rehash the exact bytes supplied to an upload. The trusted inventory must cover every byte that can become reachable from the pointer, including the manifest itself.
3. Fetch the authoritative channel ref and read `channel.json` at that exact object ID. Verify its schema, manifest digest and revision; obtain and verify the current manifest and its assets as necessary to establish the authoritative game version, rejecting regressions. A missing ref, unavailable version, malformed pointer, unavailable asset, incompatible revision, or uncertain remote state is a stop, not a reason to assume revision zero. Preserve the fetched exact object ID as the expected CAS value.
4. List release assets with pagination and detect duplicate/case-colliding names. For each expected name, read actual remote bytes in full, require correct length and SHA-256, and compare against the trusted inventory. Metadata digests or successful uploads alone are not sufficient. Distinguish confirmed absence from listing/download errors or inconsistent observations; only confirmed absent names are candidates for additive upload. Any mismatch, collision or uncertainty stops. Never overwrite, delete, rename or mutate legacy assets.

## State machine and serialization

* `INSPECT`: distinguish read-only remote verification from authorization to upload. If the channel already points to the independently trusted exact revision 3 manifest and digest, verify every remote object and report `REMOTE_VERIFIED` even if local staging was cleaned; this does not authorize uploads. To resume any upload, perform all checks above including the local integrity and provenance checks. Revision 3 pointing elsewhere, a newer revision, or a channel tip not matching the approved predecessor is a conflict requiring investigation.
* `PREPARE`: upload only confirmed missing immutable names, without clobber. Two operators may race: an upload conflict or ambiguous response returns to `INSPECT` and must download and verify the full object; it is never silently treated as success. After every upload, re-read and hash all expected objects uploaded so far and recheck local snapshots; missing objects not yet uploaded are allowed at this stage. Immediately before publication require and hash the complete remote set. The remote service's immutability and consistent reads must be established; if it permits deletion/replacement, permissions or another mechanism must prevent unauthorized mutation. Any global writer lock must be enforced against every actor capable of mutation, including direct API writers; a cooperative or local lock and upload retries are not sufficient.
* `ADVANCE`: create one commit whose sole intended channel change is a pointer with revision 3, the trusted manifest name/digest and exact previous pointer. Its parent must be the inspected exact channel tip. Advance the branch only by an atomic server-enforced compare-and-swap against that exact ref value, not merely an ancestor/fast-forward check. A CAS failure or lost/ambiguous response is not success: enter `RECONCILE` without another blind push. This CAS serializes channel advancement, not release asset writes; the separate immutable-asset prerequisite above remains mandatory.
* `RECONCILE`: freshly fetch the authoritative ref and reverify the pointer and every remote expected byte. If it points to the exact candidate commit and all checks pass, return `PUBLISHED`; if a descendant contains the candidate, do not claim the channel still exposes revision 3—report superseded/conflict and require review. If the old exact tip remains, rerun all checks before a new CAS; if any other tip exists, stop. An equal-looking pointer on a different commit is not proof our commit won. If any observation fails, return `UNKNOWN`, keep the hold and never claim success.

After a crash following a CAS attempt, first enter `RECONCILE` using the recorded candidate commit and expected tip. Use `PUBLISHED` only for the exact candidate commit with all bytes verified; an independently verified current pointer without proof this attempt won is `REMOTE_VERIFIED`, never `PUBLISHED`. If the journal is missing or ambiguous, report only the latter where its stricter trust conditions hold.

The journal is diagnostic only, not authority: record inventory identity, intended commit ID, expected old tip and durable phase before each attempted mutation, flushing it atomically. On crash at any instruction, discard in-memory assumptions and run `INSPECT`/`RECONCILE` from fresh authoritative reads. Never clear an uncertain updater-teardown marker based solely on a missing PID/job; the existing independent process-tree safety hold applies.

## Offline acceptance and review gates

Use a disposable local bare Git repository and in-memory/local fake asset service only; reject sockets and external commands other than local Git, with no credentials or production URLs. Include tests for: valid partially uploaded revision 3; REMOTE_VERIFIED without local files; insufficient provenance blocking uploads; fresh-revision fallback blocked when asset protection or CAS is unproven; local or remote byte, length, manifest, segment and version mismatch; missing or forged inventory; duplicate/case-colliding names and path traversal; unreadable/ambiguous listing and download; missing remote object; duplicate upload races and conflicting writers; remote mutation between checks; exact-tip CAS against an ancestor and an unrelated commit; unchanged tip after failed attempt; crash immediately before/after each upload, journal write, CAS and response; CAS success with lost response; exact candidate, equal pointer on a different commit, descendant and superseding revision; absent channel; updater marker; and asserted absence of all legacy writes. For this offline implementation and its tests, assert the original unconditional hold remains before every live publication path and is not edited or bypassed; any later hold change requires a separate independently reviewed approval. Fake failure injection must run the recovery twice and verify either exact idempotent success or a fail-closed conflict/unknown; never claim convergence under an unproven remote immutability guarantee.
